Section 01

Introducing Modules

A real project has hundreds or thousands of classes grouped into packages, and those packages are grouped into JAR files. A JAR is a zip file with some extra information and the extension .jar. When open-source libraries depend on other libraries, keeping compatible versions of every JAR available at runtime becomes what the community calls JAR hell — the wrong version of a class being loaded, or a ClassNotFoundException at runtime.

The Java Platform Module System (JPMS) groups code at a higher level than packages. The main purpose of a module is to provide groups of related packages that offer a particular set of functionality. It is like a JAR file, except the developer chooses which packages are accessible outside the module.

The Java Platform Module System includes

  • A format for module JAR files
  • Partitioning of the JDK into modules
  • Additional command-line options for Java tools

What a module actually is

A module is a group of one or more packages plus a special file called module-info.java. The contents of that file are the module declaration. Arrows between modules in a design diagram represent dependencies — one module relying on code in another.

✓ Key Rule

module-info.java is required to be inside all modules, and it must sit in the root directory of the module — not inside a package folder.

Benefits of modules

  • Better access control: beyond private/package/protected/public, you can have packages that are only accessible to other packages in the same module.
  • Clearer dependency management: since modules specify what they rely on, Java can complain about a missing JAR at startup rather than when it is first accessed at runtime.
  • Custom Java builds: create a Java runtime with only the parts of the JDK your program needs rather than the full one at over 150 MB.
  • Improved security: omitting parts of the JDK means vulnerabilities in unused parts don't matter.
  • Improved performance: a smaller Java package gives better startup time and a lower memory requirement.
  • Unique package enforcement: Java can ensure each package comes from only one module.
★ Remember

Using modules is optional. Every other Java 21 feature works without converting your application to modules. But the exam still tests the syntax heavily.

Section 02

Creating and Running a Modular Program

The book's running example is a zoo. The first module is zoo.animal.feeding, chosen because all other modules depend on it. It has one package with one class, plus the module declaration.

Creating the files

package zoo.animal.feeding;

public class Task {
   public static void main(String... args) {
      System.out.println("All fed!");
   }
}

And the simplest possible module declaration:

module zoo.animal.feeding {
}

Three differences between a module declaration and a regular class declaration

  1. module-info.java must be in the root directory of your module. Regular Java classes should be in packages.
  2. The declaration must use the keyword module — not class, interface, or enum.
  3. The module name follows the naming rules for package names. It often includes periods. Dashes (-) are not allowed, exactly as with class and package names.
⚠ Exam Trap 
class dragon {              // DOES NOT COMPILE
   exports com.dragon.fire;
}

A module declaration that starts with class (or interface) never compiles, no matter how correct the directives inside look. The exam loves hiding this in line 1 while you scan lines 2–5 for the "real" error.

Directory structure

feeding is the module directory, and module-info.java sits directly under it. Just as with a regular JAR, the zoo.animal.feeding package has one subfolder per portion of the name, and Task is in the deepest subfolder. A mods directory is created at the same level as the module to store module artifacts later. That directory can be named anything; mods is just a common name.

feeding
 ├── module-info.java
 └── zoo
      └── animal
           └── feeding
                └── Task.java
mods            // sibling of feeding, holds the JARs

Compiling

javac --module-path mods
   -d feeding
   feeding/zoo/animal/feeding/*.java feeding/module-info.java
  • -d feeding — directory to place the generated class files in.
  • The end of the command is the list of .java files to compile; individually or via a wildcard.
  • --module-path mods — location of any custom module files. Here it could have been omitted since there are no dependencies. Think of module-path as replacing classpath for a modular program.

All four of these are valid alternatives using the short form -p:

javac -p mods -d feeding feeding/zoo/animal/feeding/*.java feeding/*.java
javac -p mods -d feeding feeding/zoo/animal/feeding/*.java feeding/module-info.java
javac -p mods -d feeding feeding/zoo/animal/feeding/Task.java feeding/module-info.java
javac -p mods -d feeding feeding/zoo/animal/feeding/Task.java feeding/*.java
javac options

★ Remember

The classpath option still exists in three forms: -cp, --class-path, and -classpath. They are common when writing nonmodular programs.

Running

The syntax is the module name, a slash, then the fully qualified class name.

java --module-path feeding
   --module zoo.animal.feeding/zoo.animal.feeding.Task

java -p feeding
   -m zoo.animal.feeding/zoo.animal.feeding.Task
⚠ Exam Trap

Only one slash appears, and it separates module from class. Everything inside the class name uses periods:

  • -m zoo.animal.talks/zoo/animal/talks/Peacocks — wrong, package parts must use dots.
  • -m n.c — wrong, missing the slash.
  • -m n-c — wrong, a dash is not a separator.
  • --module-path x-x -m n/c — correct. x-x is legal because a module path is a folder name, and folder names may contain dashes.
Use forAbbreviationLong form
Module name-m <name>--module <name>
Module path-p <path>--module-path <path>

Packaging

jar -cvf mods/zoo.animal.feeding.jar -C feeding/ .

There is nothing module-specific here — this packages everything under feeding into zoo.animal.feeding.jar in mods. Now the same run command works against the module path:

java -p mods -m zoo.animal.feeding/zoo.animal.feeding.Task

The command is identical to the earlier one except the directory. Since the module path now points at mods, a module JAR is being run.

Section 03

Updating Our Example for Multiple Modules

exports — updating the feeding module

The exports directive indicates that a module intends for those packages to be used by Java code outside the module. Without an exports directive, the module is only available to be run from the command line on its own.

module zoo.animal.feeding {
   exports zoo.animal.feeding;
}
⚠ Exam Trap

An empty module such as module com.food.supplier {} exports no packages — but a main() method inside it can still be run from the command line. "Not exported" restricts other modules, not the launcher.

requires — the care module

zoo.animal.care has two packages. zoo.animal.care.medical is intended for other modules; zoo.animal.care.details is internal and is never exported.

// HippoBirthday.java
package zoo.animal.care.details;
import zoo.animal.feeding.*;
public class HippoBirthday {
   private Task task;
}

// Diet.java
package zoo.animal.care.medical;
public class Diet { }
1: module zoo.animal.care {
2:    exports zoo.animal.care.medical;
3:    requires zoo.animal.feeding;
4: }
  • Line 1 — the module name.
  • Line 2 — the one package exported for use by other modules.
  • Line 3 — requires specifies that another module is needed. Note that the internal package zoo.animal.care.details is the one that actually uses Task; requiring is per-module, not per-package.
javac -p mods -d care
   care/zoo/animal/care/details/*.java
   care/zoo/animal/care/medical/*.java
   care/module-info.java

jar -cvf mods/zoo.animal.care.jar -C care/ .
★ Remember

The packages begin with the same prefix as the module name, and this is intentional. Think of it as the module name "claiming" the matching package and all subpackages.

Multiple exports and requires — the talks module

1: module zoo.animal.talks {
2:    exports zoo.animal.talks.content;
3:    exports zoo.animal.talks.media;
4:    exports zoo.animal.talks.schedule;
5:
6:    requires zoo.animal.feeding;
7:    requires zoo.animal.care;
8: }

Lines 2–4 allow other modules to reference all three packages; lines 6–7 list the two modules this one depends on. Each package needs its own exports line; you cannot list several after one keyword.

No exports at all — the staff module

zoo.staff requires three modules and exposes nothing:

module zoo.staff {
   requires zoo.animal.feeding;
   requires zoo.animal.care;
   requires zoo.animal.talks;
}
✓ Key Rule

Read the arrows in a module diagram literally: an arrow from a module to another is a requires in the source module and an exports in the target module. Count arrows out of a module = number of requires statements.

Section 04

Diving into the Module Declaration

★ Remember

Directives can appear in any order in the module declaration. Grouping all exports before all requires is a style choice, not a rule.

Exporting a package to a specific module

module zoo.animal.talks {
   exports zoo.animal.talks.content to zoo.staff;
   exports zoo.animal.talks.media;
   exports zoo.animal.talks.schedule;

   requires zoo.animal.feeding;
   requires zoo.animal.care;
}

From zoo.staff nothing has changed. No other module is allowed to access zoo.animal.talks.content. This is called a qualified export.

What "exporting a package" actually exposes

  • All public classes, interfaces, enums, and records are exported.
  • Any public and protected fields and methods in those files are visible.
  • private members are not visible — they are not accessible outside the class anyway.
  • Package-private members are not visible — they are not accessible outside the package anyway.
LevelWithin module codeOutside module
privateAvailable only within classNo access
PackageAvailable only within packageNo access
protectedAvailable only within package or to subclassesAccessible to subclasses only if package is exported
publicAvailable to all classesAccessible only if package is exported
⚠ Exam Trap

public is no longer the top of the access ladder. A public class in a non-exported package is invisible outside the module. The exam phrases this as "which module can reference package X" — check exports first, access modifier second.

requires transitive

requires moduleName says the current module depends on moduleName. requires transitive moduleName means that any module that requires this module will also depend on moduleName.

module zoo.animal.feeding {
   exports zoo.animal.feeding;
}

module zoo.animal.care {
   exports zoo.animal.care.medical;
   requires transitive zoo.animal.feeding;
}

module zoo.animal.talks {
   exports zoo.animal.talks.content to zoo.staff;
   exports zoo.animal.talks.media;
   exports zoo.animal.talks.schedule;
   // no longer needed requires zoo.animal.feeding;
   // no longer needed requires zoo.animal.care;
   requires transitive zoo.animal.care;
}

module zoo.staff {
   // no longer needed requires zoo.animal.feeding;
   // no longer needed requires zoo.animal.care;
   requires zoo.animal.talks;
}

Effects of applying transitive to requires zoo.animal.feeding in zoo.animal.care

  • zoo.animal.talks can optionally declare that it requires zoo.animal.feeding, but it is not required.
  • zoo.animal.care cannot be compiled or executed without access to zoo.animal.feeding.
  • zoo.animal.talks cannot be compiled or executed without access to zoo.animal.care.

These hold even if zoo.animal.care and zoo.animal.talks never reference any package in zoo.animal.feeding.

Duplicate requires statements

module bad.module {
   requires zoo.animal.talks;
   requires transitive zoo.animal.talks;   // DOES NOT COMPILE
}
  • Java does not allow you to repeat the same module in a requires clause — it is redundant and most likely a coding error.
  • requires transitive is requires plus extra behavior, so mixing the two forms is still a duplicate.
  • The second statement is the one flagged. On the exam ("which is the first line to contain a compiler error?"), pick the later line.

opens — enabling reflection

Reflection lets callers inspect and call code at runtime, and can even subvert access control. Because it is dangerous, the module system requires developers to explicitly allow it.

module zoo.animal.talks {
   opens zoo.animal.talks.schedule;
   opens zoo.animal.talks.media to zoo.staff;
}

The first allows any module using this one to use reflection. The second grants that privilege only to zoo.staff.

Opening an entire module

open module zoo.animal.talks {
}

open module zoo.animal.talks {
   opens zoo.animal.talks.schedule;    // DOES NOT COMPILE
}
⚠ Exam Trap

A module that uses the open modifier is not permitted to use the opens directive — the packages are already open. Watch the single letter s: open is a module modifier, opens is a directive.

exports

  • Compile-time and runtime access
  • Exposes public/protected members of public types
  • exports pkg; / exports pkg to mod;

opens

  • Runtime reflective access
  • Declared per package, or whole module via open module
  • opens pkg; / opens pkg to mod;
Section 05

Creating a Service

A service is composed of an interface, any classes the interface references, and a way of looking up implementations of the interface. The implementations are not part of the service. The book's example uses four modules; you are not required to have four, but that is what the exam will show.

1. The service provider interface — zoo.tours.api

// Souvenir.java
package zoo.tours.api;
public record Souvenir(String description) { }

// Tour.java
package zoo.tours.api;
public interface Tour {
   String name();
   int length();
   Souvenir getSouvenir();
}

// module-info.java
module zoo.tours.api {
   exports zoo.tours.api;
}

All three interface methods use the implicit public modifier. Souvenir is part of the service because the interface references it. A service provider "interface" may be an abstract class, but the exam only shows an interface.

2. The service locator — zoo.tours.reservations

// TourFinder.java
package zoo.tours.reservations;

import java.util.*;
import zoo.tours.api.*;

public class TourFinder {
   public static Tour findSingleTour() {
      ServiceLoader<Tour> loader = ServiceLoader.load(Tour.class);
      for (Tour tour : loader)
         return tour;
      return null;
   }
   public static List<Tour> findAllTours() {
      List<Tour> tours = new ArrayList<>();
      ServiceLoader<Tour> loader = ServiceLoader.load(Tour.class);
      for (Tour tour : loader)
         tours.add(tour);
      return tours;
   }
}

// module-info.java
module zoo.tours.reservations {
   exports zoo.tours.reservations;
   requires zoo.tours.api;
   uses zoo.tours.api.Tour;
}
✓ Key Rule

Both requires and uses are needed — one for compilation, one for lookup. uses takes the fully qualified interface name, not a package.

ServiceLoader methods you must know

public final class ServiceLoader<S> implements Iterable<S> {
   public static <S> ServiceLoader<S> load(Class<S> service) { ... }
   public Stream<Provider<S>> stream() { ... }
}

Looping over the loader gives you the service type directly. Requesting a Stream gives a different type — a Stream<Provider<S>>, because a stream controls when elements are evaluated. You must call get() on each Provider:

ServiceLoader.load(Tour.class)
  .stream()
  .map(Provider::get)
  .mapToInt(Tour::length)
  .max()
  .ifPresent(System.out::println);
⚠ Exam Trap
  • There is no getStream() method on ServiceLoader.
  • ServiceLoader.load(X.class).stream().toList() does not compile as a List<X> — it is a list of Provider. You need .map(Provider::get) in between.
  • ServiceLoader.load() is relatively expensive; in a real application, cache the result.

3. The consumer — zoo.visitor

// Tourist.java
package zoo.visitor;

import java.util.*;
import zoo.tours.api.*;
import zoo.tours.reservations.*;

public class Tourist {
   public static void main(String[] args) {
      Tour tour = TourFinder.findSingleTour();
      System.out.println("Single tour: " + tour);

      List<Tour> tours = TourFinder.findAllTours();
      System.out.println("# tours: " + tours.size());
   }
}

// module-info.java
module zoo.visitor {
   requires zoo.tours.api;
   requires zoo.tours.reservations;
}

Running it before any implementation exists:

java -p mods -m zoo.visitor/zoo.visitor.Tourist

Single tour: null
# tours: 0
  • findSingleTour() finds no providers, so the enhanced for loop body never runs and null is returned.
  • String concatenation with a null reference prints the text null — no NullPointerException.
  • findAllTours() returns an empty (not null) list, so size() is 0.

4. The service provider — zoo.tours.agency

// TourImpl.java
package zoo.tours.agency;
import zoo.tours.api.*;

public class TourImpl implements Tour {
   public String name()      { return "Behind the Scenes"; }
   public int length()       { return 120; }
   public Souvenir getSouvenir() {
      return new Souvenir("stuffed animal");
   }
}

// module-info.java
module zoo.tours.agency {
   requires zoo.tours.api;
   provides zoo.tours.api.Tour with zoo.tours.agency.TourImpl;
}

The package containing the implementation is not exported — callers should not refer to it directly. The syntax is:

provides interfaceName with className;

After packaging the provider and rerunning the same command:

Single tour: zoo.tours.agency.TourImpl@1936f0f5
# tours: 1
✓ Key Rule

Nothing was recompiled. Adding a new service provider module requires zero recompiles of existing modules — the service locator simply observes the new provider on the module path. This is loose coupling in action.

⚠ Exam Trap

provides takes the interface first and the implementation second, joined by with. Wrong forms the exam offers: provides Impl with Interface, provides Interface by Impl, provides Interface using Impl. Only with exists.

Section 06

Discovering Modules

You do not need to know the output of these commands. You do need to know the syntax of the commands and what they do.

Identifying built-in modules

java.base contains most of the packages covered on the exam. You never need requires java.base — it is available to all modular applications. The file still compiles if you write it explicitly, but it is redundant, so omit it. It is analogous to java.lang being imported automatically in a class.

java.desktopAWT and SwingNot on exam beyond module name
java.loggingLoggingNot on exam beyond module name

⚠ Exam Trap
  • Module names beginning with java are APIs you are likely to use; those beginning with jdk are specific to the JDK. There are about 20 java.* and about 30 jdk.* modules.
  • java.util is a package, not a module. jdk.base does not exist — the module is java.base.
  • You don't have to memorize the lists, but you must be able to pick real module names out of a lineup of invented ones.

Describing a module

These two commands are equivalent:

java -p mods -d zoo.animal.feeding
java -p mods --describe-module zoo.animal.feeding
zoo.animal.feeding file:///absolutePath/mods/zoo.animal.feeding.jar
exports zoo.animal.feeding
requires java.base mandated
  • requires java.base mandated appears even though the declaration requires nothing — java.base is added automatically to every module. The word mandated comes last.
  • A qualified export shows as qualified exports zoo.animal.care.medical to zoo.staff.
  • contains zoo.animal.care.details means a package exists in the module that is not exported at all.
⚠ Exam Trap

-d means two different things depending on the command:

  • javac -d <dir> — the output directory for class files.
  • java -d <module> — short form of --describe-module.
  • jar -d — also --describe-module.

Listing available modules and showing resolution

java --list-modules              // ~70 lines: java.base@21, java.compiler@21, ...
java -p mods --list-modules      // adds custom modules with their file paths

java --show-module-resolution
   -p feeding
   -m zoo.animal.feeding/zoo.animal.feeding.Task

--list-modules

  • Lists observable modules
  • Exits as soon as it prints — does not run the program
  • JDK modules show a version (@21); custom modules show a file path

--show-module-resolution

  • Debugging view of module resolution
  • Prints a lot of output, then runs the program (output ends with All fed!)
  • Starts by listing the root module

Describing with jar

jar -f mods/zoo.animal.feeding.jar -d
jar --file mods/zoo.animal.feeding.jar --describe-module

The output differs only in that the JAR version includes module-info.class in the filename. What matters for the exam: both java and jar can describe a module.

jdeps — learning about dependencies

Unlike describing a module, jdeps looks at the code in addition to the module declaration, so it tells you what dependencies are actually used rather than simply declared. It is the tool for projects that have not yet been modularized.

package zoo.dinos;
import java.time.*;
import java.util.*;
import sun.misc.Unsafe;

public class Animatronic {
   private List<String> names;
   private LocalDate visitDate;
   ...
   public void unsafeMethod() {
      Unsafe unsafe = Unsafe.getUnsafe();
   }
}

  • --jdk-internals lists any classes calling an internal API, plus a table of suggested replacements.
  • jdk.unsupported is not in the published module lists — it holds internal libraries you should not reference, as they may disappear.
  • jdeps has a --module-path option with no short form, unlike other commands.

jmod

Oracle recommends JAR files for most modules. JMOD files are recommended only when you have native libraries or something that can't go inside a JAR. The one thing to remember: jmod is only for working with JMOD files.

jlink and jpackage

jlink --module-path mods --add-modules zoo.animal.talks --output zooApp

This creates a runtime image: a folder containing bin, conf, include, legal, lib, man and a release file — about 15 MB zipped versus a 150 MB+ JDK. It is not a single image file.

jpackage --name feedingTask --module-path mods
   --module zoo.animal.feeding/zoo.animal.feeding.Task

This creates an application image: a single executable for a specific platform (.exe on Windows, .dmg on Mac — here feedingTask-1.0.dmg). For a non-modular JAR:

jpackage --name myApp --input myDir --main-class com.wiley.java.Cat
   --main-jar myApp.jar

jlink

  • Output: runtime image = a directory
  • Modular applications only
  • -p/--module-path, --add-modules, --output

jpackage

  • Output: application image = a single executable
  • Modular and non-modular applications
  • -n/--name, -i/--input, --main-class, --main-jar, --app-version (defaults to 1.0)

Both provide the parts of Java needed to run, and for both, a JDK need not already be installed on the target system.

★ Remember

jimage is used to inspect a Java image file — it does not create one. If a question asks which commands create an .exe and a directory respectively, the answer is jpackage and jlink.

Section 07

Comparing Types of Modules

Named modules

A named module contains a module-info.java file in the root of the JAR alongside one or more packages, and appears on the module path. Unless otherwise specified, a module is a named module. Memory aid: a named module has the name inside module-info.java and is on the module path.

★ Remember

From Chapter 7: the only way for subclasses of a sealed class to live in a different package is to be within the same named module.

Automatic modules

An automatic module appears on the module path but does not contain a module-info.java file — a regular JAR placed on the module path and treated as a module. Java automatically determines the module name, and code referencing it behaves as if a module-info.java were present. It automatically exports all packages.

Library authors were encouraged to declare their intended module name by adding an Automatic-Module-Name property to META-INF/MANIFEST.MF. The manifest is a text file of key/value pairs separated by a colon; the default in Java 21 is:

Manifest-Version: 1.0
Created-By: 21 (Oracle Corporation)

Algorithm for determining an automatic module name

  1. If the MANIFEST.MF specifies an Automatic-Module-Name, use that and stop.
  2. Remove the file extension from the JAR name.
  3. Remove any version information from the end of the name. A version is digits and dots with possible extra information at the end — for example -1.0.0 or -1.0-RC.
  4. Replace any remaining characters other than letters and numbers with dots.
  5. Replace any sequences of dots with a single dot.
  6. Remove the dot if it is the first or last character of the result.

⚠ Exam Trap
  • emily-1.0.0.jar → emily · emily-1.0.0-SNAPSHOT.jar → emily (the trailing tag goes with the version).
  • emily_the_cat-1.0.0.jar → emily.the.cat. Underscores become dots, not dashes, and dashes are never allowed in a module name.
  • emily.$.jar → emily. The $ becomes a dot, giving emily.., which collapses to emily., and the trailing dot is removed.

Unnamed modules

An unnamed module appears on the classpath. Like an automatic module it is a regular JAR; unlike an automatic module it is on the classpath rather than the module path, so it is treated as old code and a second-class citizen. It usually contains no module-info.java; if it happens to contain one, that file is ignored because it is on the classpath. Unnamed modules do not export any packages to named modules, but can read from any JARs on the classpath or module path.

✓ Key Rule

Code on the classpath can access the module path. Code on the module path cannot read from the classpath. This single asymmetry answers many exam questions.

Section 08

Migrating an Application

Determining the order

Dependencies between projects form a graph. Arrows point from the project that requires the dependency to the one that makes it available — in module language, from requires to exports. Projects with no dependencies are at the bottom; projects that depend on others are at the top. When two projects have no arrow between them, either order is allowed.

Bottom-up migration

  1. Pick the lowest-level project not yet migrated.
  2. Add module-info.java with exports for packages used by higher-level JARs and requires for its dependencies.
  3. Move that named module from the classpath to the module path.
  4. Leave not-yet-migrated projects as unnamed modules on the classpath.
  5. Repeat with the next-lowest project.

Best when you can convert every JAR. Mix during migration: named + unnamed.

Top-down migration

  1. Place all projects on the module path.
  2. Pick the highest-level project not yet migrated.
  3. Add module-info.java to convert that automatic module into a named module; use other modules' automatic module names in requires.
  4. Repeat with the next-highest project.

Best when you don't control every JAR. Mix during migration: named + automatic.

CategoryBottom-UpTop-Down
Project that depends on all othersUnnamed module on classpathNamed module on module path
Project that has no dependenciesNamed module on module pathAutomatic module on module path
⚠ Exam Trap

"For a top-down migration, all modules other than named modules are ______ and are on the ______." → automatic, module path. Top-down starts by putting everything on the module path, so nothing stays on the classpath.

Splitting a big project into modules

Break packages into logical groupings and draw the dependencies. There will usually be fewer modules than packages because some packages share a module. The JPMS does not allow cyclic dependencies: if zoo.tickets.delivery requires zoo.tickets.discount, then zoo.tickets.discount is not allowed to require zoo.tickets.delivery. The common fix is to introduce another module holding the shared code, breaking the cycle.

Failing to compile with a cyclic dependency

// Butterfly.java
package zoo.butterfly;
public class Butterfly {
   private Caterpillar caterpillar;
}
// module-info.java
module zoo.butterfly {
   exports zoo.butterfly;
   requires zoo.caterpillar;
}

// Caterpillar.java
package zoo.caterpillar;
public class Caterpillar {
   Butterfly emergeCocoon() { // logic omitted }
}
// module-info.java
module zoo.caterpillar {
   exports zoo.caterpillar;
   requires zoo.butterfly;   // stalemate — neither module can be compiled
}
  • zoo.butterfly can't compile until zoo.caterpillar is built.
  • zoo.caterpillar can't compile until zoo.butterfly is built.
  • Neither module can ever be compiled. The module system prevents cyclic dependencies at compile time — that's a feature, not a bug.
  • Three modules behave the same way: if ballA requires ballB and ballB requires ballC, then ballC cannot require ballA.
✓ Key Rule

Java does allow a cyclic dependency between packages within a module. It only forbids cycles between modules. A cyclic dependency always involves at least two requires statements, and may involve two or more modules.

Short Recap

Introducing modules

  • JPMS = format for module JARs + partitioning of the JDK + extra command-line options; it solves JAR hell.
  • A module = one or more packages + module-info.java in the module's root directory.

Creating and running

  • javac -p mods -d outDir files… module-info.java; java -p mods -m moduleName/package.ClassName; jar -cvf mods/x.jar -C dir/ .
  • One slash between module and class; everything else uses dots. Module names allow dots, never dashes.

Directives

  • exports (optionally to), requires / requires transitive, opens (optionally to), provides … with …, uses. Any order.
  • Repeating a module in two requires clauses does not compile; open module plus opens does not compile.
  • public only reaches outside the module if the package is exported.

Services

  • Service = service provider interface + service locator. The service provider (implementation) and the consumer are not part of the service.
  • SPI: exports. Locator: exports, requires, uses. Provider: requires, provides. Consumer: requires.
  • ServiceLoader.load() is iterable; stream() returns Stream<Provider<S>> and needs .map(Provider::get).

Discovering modules

  • java -d / --describe-module, --list-modules (doesn't run), --show-module-resolution (does run), jar -f x.jar -d.
  • jdeps (-s/-summary, --jdk-internals/-jdkinternals); jmod for JMOD files; jlink → directory; jpackage → executable.
  • requires java.base mandated shows for every module.

Module types

  • Named = module-info + module path. Automatic = no module-info + module path, exports everything. Unnamed = classpath, exports nothing to named modules.
  • Automatic module name: manifest wins; else strip extension and version, special chars → dots, collapse dots, trim edge dots.

Migration

  • Bottom-up: lowest first, unmigrated stay unnamed on the classpath. Top-down: everything on the module path first, unmigrated are automatic.
  • Cycles between modules never compile; cycles between packages inside one module are fine.

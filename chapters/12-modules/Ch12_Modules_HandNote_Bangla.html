Section 01

Modules-এর পরিচয়

বাস্তব প্রজেক্টে শত শত বা হাজার হাজার class থাকে, যেগুলো package-এ ভাগ করা হয়, আর সেই package-গুলো JAR ফাইলে গোছানো হয়। JAR আসলে একটা zip ফাইল যাতে কিছু বাড়তি তথ্য থাকে, extension হলো .jar। যখন এক open-source library আরেক library-র উপর নির্ভর করে, তখন runtime-এ সব JAR-এর compatible version রাখা কঠিন হয়ে যায় — community এই সমস্যাকে বলে JAR hell। ভুল version-এর class লোড হওয়া, কিংবা runtime-এ ClassNotFoundException — এগুলোই এর লক্ষণ।

Java Platform Module System (JPMS) package-এর চেয়েও উপরের স্তরে code সংগঠিত করে। একটি module-এর মূল উদ্দেশ্য হলো সম্পর্কিত package-এর একটি গ্রুপ দেওয়া যা নির্দিষ্ট কিছু functionality প্রদান করে। এটা অনেকটা JAR ফাইলের মতোই, তবে পার্থক্য হলো — developer নিজে ঠিক করে দেয় কোন package গুলো module-এর বাইরে থেকে accessible হবে।

Java Platform Module System-এ যা যা আছে

  • Module JAR ফাইলের একটি format
  • JDK-কে module-এ ভাগ করা (partitioning)
  • Java tool-গুলোর জন্য অতিরিক্ত command-line option

Module আসলে কী

একটি module মানে এক বা একাধিক package + module-info.java নামের একটি বিশেষ ফাইল। এই ফাইলের ভেতরের বিষয়বস্তুকেই বলে module declaration। Design ডায়াগ্রামে module-গুলোর মাঝে যে তীরচিহ্ন থাকে সেগুলো হলো dependency — অর্থাৎ একটি module আরেকটির code-এর উপর নির্ভরশীল।

✓ KEY RULE

module-info.java প্রতিটি module-এ থাকা বাধ্যতামূলক, এবং এটি থাকতে হবে module-এর root directory-তে — কোনো package folder-এর ভেতরে নয়।

Module-এর সুবিধাগুলো

  • Better access control: private/package/protected/public-এর বাইরেও এমন package রাখা যায় যা শুধু একই module-এর অন্য package থেকে accessible।
  • Clearer dependency management: module যেহেতু নিজের নির্ভরতা ঘোষণা করে, তাই Java missing JAR-এর অভিযোগ program startup-এই করতে পারে, runtime-এ প্রথম access-এর সময় নয়।
  • Custom Java builds: ১৫০ MB+ পুরো JDK-র বদলে শুধু প্রয়োজনীয় অংশ নিয়ে Java runtime বানানো যায়।
  • Improved security: JDK-র যে অংশ বাদ দিয়েছেন, সেই অংশের vulnerability নিয়ে আর চিন্তা করতে হয় না।
  • Improved performance: ছোট package মানে দ্রুত startup time এবং কম memory প্রয়োজন।
  • Unique package enforcement: Java নিশ্চিত করতে পারে প্রতিটি package শুধু একটি module থেকেই আসছে।
★ REMEMBER

Module ব্যবহার করা optional। Java 21-এর বাকি সব feature module-এ convert না করেও ব্যবহার করা যায়। কিন্তু exam-এ এর syntax খুব ভালোভাবেই পরীক্ষা করা হয়।

Section 02

Modular প্রোগ্রাম তৈরি ও চালানো

বইয়ের চলমান উদাহরণ হলো একটি zoo। প্রথম module হলো zoo.animal.feeding — একে দিয়ে শুরু করা হয়েছে কারণ বাকি সব module এর উপর নির্ভর করে। এতে একটি package, একটি class এবং module declaration আছে।

ফাইল তৈরি

package zoo.animal.feeding;

public class Task {
   public static void main(String... args) {
      System.out.println("All fed!");
   }
}

আর সবচেয়ে সরল module declaration:

module zoo.animal.feeding {
}

Module declaration ও সাধারণ class declaration-এর ৩টি পার্থক্য

  1. module-info.java থাকতে হবে module-এর root directory-তে। সাধারণ class থাকে package-এর ভেতরে।
  2. Declaration-এ module keyword ব্যবহার করতে হবে — class, interface বা enum নয়।
  3. Module name package name-এর naming rule মেনে চলে। এতে সাধারণত period (.) থাকে। Dash (-) allowed নয় — ঠিক যেমন class ও package name-এ allowed নয়।
⚠ EXAM TRAP 
class dragon {              // DOES NOT COMPILE
   exports com.dragon.fire;
}

class (বা interface) দিয়ে শুরু হওয়া module declaration কখনোই compile হয় না — ভেতরের directive যতই সঠিক দেখাক। Exam প্রায়ই এই ভুলটা line 1-এ লুকিয়ে রাখে, আর আপনি line 2–5-এ "আসল" ভুল খুঁজতে থাকেন।

Directory structure

feeding হলো module directory, আর module-info.java সরাসরি তার নিচে। সাধারণ JAR-এর মতোই zoo.animal.feeding package-এর নামের প্রতিটি অংশের জন্য একটি করে subfolder থাকে, এবং Task class থাকে সবচেয়ে ভেতরের folder-এ। Module artifact রাখার জন্য module-এর পাশেই একটি mods directory বানানো হয়। এই directory-র নাম যেকোনো কিছু হতে পারে; mods শুধু প্রচলিত নাম।

feeding
 ├── module-info.java
 └── zoo
      └── animal
           └── feeding
                └── Task.java
mods            // feeding-এর সমপর্যায়ে, JAR রাখার জন্য

Compile করা

javac --module-path mods
   -d feeding
   feeding/zoo/animal/feeding/*.java feeding/module-info.java
  • -d feeding — generated class ফাইল কোন directory-তে যাবে।
  • Command-এর শেষে compile করার .java ফাইলের তালিকা; আলাদা আলাদা লিখুন বা wildcard দিন।
  • --module-path mods — custom module ফাইলের অবস্থান। এখানে dependency নেই বলে এটা বাদ দিলেও চলত। Modular program-এ module-path কে classpath-এর বিকল্প ভাবতে পারেন।

নিচের চারটিই বৈধ বিকল্প, short form -p ব্যবহার করে:

javac -p mods -d feeding feeding/zoo/animal/feeding/*.java feeding/*.java
javac -p mods -d feeding feeding/zoo/animal/feeding/*.java feeding/module-info.java
javac -p mods -d feeding feeding/zoo/animal/feeding/Task.java feeding/module-info.java
javac -p mods -d feeding feeding/zoo/animal/feeding/Task.java feeding/*.java
কীসের জন্যAbbreviationLong form
Class ফাইলের directory-d <dir>n/a
Module path-p <path>--module-path <path>
★ REMEMBER

classpath option এখনো তিন রূপে আছে: -cp, --class-path এবং -classpath। Nonmodular program লেখার সময় এগুলো এখনো খুব সাধারণ।

Run করা

Syntax হলো — module name, তারপর একটি slash, তারপর fully qualified class name।

java --module-path feeding
   --module zoo.animal.feeding/zoo.animal.feeding.Task

java -p feeding
   -m zoo.animal.feeding/zoo.animal.feeding.Task
⚠ EXAM TRAP

Slash থাকে মাত্র একটি, আর সেটা module ও class-কে আলাদা করে। Class name-এর ভেতরের সব অংশে period ব্যবহার হয়:

  • -m zoo.animal.talks/zoo/animal/talks/Peacocks — ভুল, package অংশে dot লাগবে।
  • -m n.c — ভুল, slash নেই।
  • -m n-c — ভুল, dash কোনো separator নয়।
  • --module-path x-x -m n/c — সঠিক। x-x বৈধ কারণ module path একটি folder name, আর folder name-এ dash allowed।
কীসের জন্যAbbreviationLong form
Module name-m <name>--module <name>
Module path-p <path>--module-path <path>

Package করা (JAR বানানো)

jar -cvf mods/zoo.animal.feeding.jar -C feeding/ .

এখানে module-specific কিছুই নেই — feeding-এর সবকিছু নিয়ে mods folder-এ zoo.animal.feeding.jar তৈরি হচ্ছে। এবার একই run command module path দিয়ে চালানো যায়:

java -p mods -m zoo.animal.feeding/zoo.animal.feeding.Task

আগের command-এর সাথে এর একমাত্র পার্থক্য হলো directory। Module path এখন mods-এ, তাই এবার একটি module JAR রান হচ্ছে।

Section 03

একাধিক Module-এর জন্য উদাহরণ আপডেট

exports — feeding module আপডেট

exports directive দিয়ে বোঝানো হয় যে module চায় ওই package-গুলো তার বাইরের Java code ব্যবহার করুক। exports না থাকলে module শুধু command line থেকে একা রান করার জন্যই available থাকে।

module zoo.animal.feeding {
   exports zoo.animal.feeding;
}
⚠ EXAM TRAP

module com.food.supplier {} — এই খালি module কোনো package export করে না, কিন্তু এর ভেতরের main() method command line থেকে রান করা যাবে। "Export করা হয়নি" মানে অন্য module-এর জন্য বন্ধ, launcher-এর জন্য নয়।

requires — care module

zoo.animal.care-এ দুটি package। zoo.animal.care.medical অন্য module-এর জন্য, আর zoo.animal.care.details শুধু ভেতরের ব্যবহারের জন্য — কখনো export হয় না।

// HippoBirthday.java
package zoo.animal.care.details;
import zoo.animal.feeding.*;
public class HippoBirthday {
   private Task task;
}

// Diet.java
package zoo.animal.care.medical;
public class Diet { }
1: module zoo.animal.care {
2:    exports zoo.animal.care.medical;
3:    requires zoo.animal.feeding;
4: }
  • Line 1 — module-এর নাম।
  • Line 2 — যে একটি package অন্য module-এর জন্য export করা হচ্ছে।
  • Line 3 — requires বলে দেয় আরেকটি module প্রয়োজন। খেয়াল করুন, Task আসলে ব্যবহার করছে internal package zoo.animal.care.details — তবু requires হয় module ধরে, package ধরে নয়।
javac -p mods -d care
   care/zoo/animal/care/details/*.java
   care/zoo/animal/care/medical/*.java
   care/module-info.java

jar -cvf mods/zoo.animal.care.jar -C care/ .
★ REMEMBER

Package-গুলোর নাম module name-এর মতো একই prefix দিয়ে শুরু হয়েছে — এটা ইচ্ছাকৃত। ভাবতে পারেন module name তার সমনামের package ও সব subpackage "দাবি" করে নেয়।

একাধিক exports ও requires — talks module

1: module zoo.animal.talks {
2:    exports zoo.animal.talks.content;
3:    exports zoo.animal.talks.media;
4:    exports zoo.animal.talks.schedule;
5:
6:    requires zoo.animal.feeding;
7:    requires zoo.animal.care;
8: }

Line 2–4 তিনটি package-কেই অন্য module থেকে ব্যবহারযোগ্য করে; line 6–7 বলে দেয় এই module কোন দুটি module-এর উপর নির্ভরশীল। প্রতিটি package-এর জন্য আলাদা exports line লাগবে — এক keyword-এর পরে কমা দিয়ে অনেকগুলো লেখা যায় না।

কোনো exports নেই — staff module

zoo.staff তিনটি module require করে, কিন্তু কিছুই expose করে না:

module zoo.staff {
   requires zoo.animal.feeding;
   requires zoo.animal.care;
   requires zoo.animal.talks;
}
✓ KEY RULE

Module ডায়াগ্রামের তীরচিহ্ন আক্ষরিকভাবে পড়ুন: একটি module থেকে অন্য module-এ যাওয়া তীর মানে উৎস module-এ requires এবং লক্ষ্য module-এ exports। কোনো module থেকে বের হওয়া তীরের সংখ্যা = তার requires statement-এর সংখ্যা।

Section 04

Module Declaration-এর গভীরে

★ REMEMBER

Module declaration-এ directive গুলো যেকোনো ক্রমে লেখা যায়। সব exports আগে আর সব requires পরে লেখাটা স্টাইলের ব্যাপার, নিয়ম নয়।

নির্দিষ্ট module-এ package export

module zoo.animal.talks {
   exports zoo.animal.talks.content to zoo.staff;
   exports zoo.animal.talks.media;
   exports zoo.animal.talks.schedule;

   requires zoo.animal.feeding;
   requires zoo.animal.care;
}

zoo.staff-এর দিক থেকে কিছুই বদলায়নি। কিন্তু অন্য কোনো module আর zoo.animal.talks.content ব্যবহার করতে পারবে না। একে বলে qualified export।

"Package export করা" আসলে কী কী উন্মুক্ত করে

  • সব public class, interface, enum এবং record export হয়।
  • ওই ফাইলগুলোর public ও protected field ও method দৃশ্যমান হয়।
  • private সদস্য দৃশ্যমান হয় না — কারণ class-এর বাইরেই তা accessible নয়।
  • Package-private সদস্য দৃশ্যমান হয় না — কারণ package-এর বাইরেই তা accessible নয়।
LevelModule-এর ভেতরেModule-এর বাইরে
privateশুধু class-এর ভেতরেকোনো access নেই
Packageশুধু package-এর ভেতরেকোনো access নেই
protectedশুধু package-এর ভেতরে বা subclass-এsubclass থেকে accessible, যদি package export করা থাকে
publicসব class-এর জন্যaccessible শুধু যদি package export করা থাকে
⚠ EXAM TRAP

public আর access ladder-এর সর্বোচ্চ ধাপ নয়। Export না করা package-এর public class module-এর বাইরে অদৃশ্য। Exam এটা জিজ্ঞেস করে "কোন module package X reference করতে পারবে" এই ভাষায় — আগে exports দেখুন, পরে access modifier।

requires transitive

requires moduleName মানে বর্তমান module ওই module-এর উপর নির্ভরশীল। আর requires transitive moduleName মানে — যে module এই module-কে requires করবে, সেও স্বয়ংক্রিয়ভাবে moduleName-এর উপর নির্ভরশীল হবে।

module zoo.animal.feeding {
   exports zoo.animal.feeding;
}

module zoo.animal.care {
   exports zoo.animal.care.medical;
   requires transitive zoo.animal.feeding;
}

module zoo.animal.talks {
   exports zoo.animal.talks.content to zoo.staff;
   exports zoo.animal.talks.media;
   exports zoo.animal.talks.schedule;
   // no longer needed requires zoo.animal.feeding;
   // no longer needed requires zoo.animal.care;
   requires transitive zoo.animal.care;
}

module zoo.staff {
   // no longer needed requires zoo.animal.feeding;
   // no longer needed requires zoo.animal.care;
   requires zoo.animal.talks;
}

zoo.animal.care-এ transitive যোগ করার ফলাফল

  • zoo.animal.talks চাইলে requires zoo.animal.feeding লিখতে পারে, কিন্তু বাধ্যতামূলক নয়।
  • zoo.animal.feeding-এ access ছাড়া zoo.animal.care compile বা execute হবে না।
  • zoo.animal.care-এ access ছাড়া zoo.animal.talks compile বা execute হবে না।

এই নিয়মগুলো তখনও প্রযোজ্য যখন zoo.animal.care ও zoo.animal.talks আসলে zoo.animal.feeding-এর কোনো package ব্যবহারই করে না।

Duplicate requires statement

module bad.module {
   requires zoo.animal.talks;
   requires transitive zoo.animal.talks;   // DOES NOT COMPILE
}
  • একই module-কে দুবার requires clause-এ লেখা Java allow করে না — এটা redundant এবং সাধারণত coding error।
  • requires transitive হলো requires + বাড়তি behavior, তাই দুই ধরন মেশালেও সেটা duplicate-ই।
  • Error ধরা পড়ে দ্বিতীয় statement-এ। "কোন line-এ প্রথম compiler error?" — উত্তরে পরের line বেছে নিন।

opens — reflection চালু করা

Reflection দিয়ে runtime-এ code পরিদর্শন ও কল করা যায়, এমনকি access control ভেঙেও ফেলা যায়। ঝুঁকিপূর্ণ বলেই module system দাবি করে যে developer module declaration-এ স্পষ্টভাবে অনুমতি দিক।

module zoo.animal.talks {
   opens zoo.animal.talks.schedule;
   opens zoo.animal.talks.media to zoo.staff;
}

প্রথমটি এই module ব্যবহারকারী যেকোনো module-কে reflection-এর অনুমতি দেয়। দ্বিতীয়টি শুধু zoo.staff-কে দেয়।

পুরো module open করা

open module zoo.animal.talks {
}

open module zoo.animal.talks {
   opens zoo.animal.talks.schedule;    // DOES NOT COMPILE
}
⚠ EXAM TRAP

যে module open modifier ব্যবহার করে, সে opens directive ব্যবহার করতে পারবে না — কারণ package গুলো তো ইতিমধ্যেই open। একটি অক্ষরের পার্থক্য খেয়াল করুন: open হলো module modifier, আর opens হলো directive।

exports

  • Compile-time ও runtime access
  • public type-এর public/protected সদস্য উন্মুক্ত করে
  • exports pkg; / exports pkg to mod;

opens

  • Runtime reflective access
  • Package ধরে, অথবা open module দিয়ে পুরো module
  • opens pkg; / opens pkg to mod;
Section 05

Service তৈরি করা

একটি service গঠিত হয় — একটি interface, interface যেসব class reference করে সেগুলো, এবং interface-এর implementation খুঁজে বের করার একটি উপায় নিয়ে। Implementation গুলো service-এর অংশ নয়। বইয়ের উদাহরণে চারটি module ব্যবহার করা হয়েছে; চারটি module বাধ্যতামূলক নয়, তবে exam-এ এভাবেই দেখানো হয়।

১. Service provider interface — zoo.tours.api

// Souvenir.java
package zoo.tours.api;
public record Souvenir(String description) { }

// Tour.java
package zoo.tours.api;
public interface Tour {
   String name();
   int length();
   Souvenir getSouvenir();
}

// module-info.java
module zoo.tours.api {
   exports zoo.tours.api;
}

তিনটি method-ই implicit public modifier ব্যবহার করছে। Souvenir service-এর অংশ, কারণ interface একে reference করে। Service provider "interface" আসলে abstract class-ও হতে পারে, তবে exam-এ শুধু interface-ই দেখবেন।

২. Service locator — zoo.tours.reservations

// TourFinder.java
package zoo.tours.reservations;

import java.util.*;
import zoo.tours.api.*;

public class TourFinder {
   public static Tour findSingleTour() {
      ServiceLoader<Tour> loader = ServiceLoader.load(Tour.class);
      for (Tour tour : loader)
         return tour;
      return null;
   }
   public static List<Tour> findAllTours() {
      List<Tour> tours = new ArrayList<>();
      ServiceLoader<Tour> loader = ServiceLoader.load(Tour.class);
      for (Tour tour : loader)
         tours.add(tour);
      return tours;
   }
}

// module-info.java
module zoo.tours.reservations {
   exports zoo.tours.reservations;
   requires zoo.tours.api;
   uses zoo.tours.api.Tour;
}
✓ KEY RULE

requires এবং uses — দুটোই লাগে। একটি compilation-এর জন্য, আরেকটি lookup-এর জন্য। uses নেয় fully qualified interface name, package name নয়।

ServiceLoader-এর যে দুটি method জানতেই হবে

public final class ServiceLoader<S> implements Iterable<S> {
   public static <S> ServiceLoader<S> load(Class<S> service) { ... }
   public Stream<Provider<S>> stream() { ... }
}

Loader-এর উপর loop করলে সরাসরি service type পাওয়া যায়। কিন্তু Stream চাইলে ভিন্ন type আসে — Stream<Provider<S>>, কারণ Stream নিয়ন্ত্রণ করে element কখন evaluate হবে। তাই প্রতিটি Provider-এর উপর get() কল করতে হয়:

ServiceLoader.load(Tour.class)
  .stream()
  .map(Provider::get)
  .mapToInt(Tour::length)
  .max()
  .ifPresent(System.out::println);
⚠ EXAM TRAP
  • ServiceLoader-এ getStream() নামে কোনো method নেই।
  • ServiceLoader.load(X.class).stream().toList() কে List<X> হিসেবে নিলে compile হয় না — ওটা Provider-এর list। মাঝে .map(Provider::get) লাগবে।
  • ServiceLoader.load() কল তুলনামূলকভাবে ব্যয়বহুল; বাস্তব application-এ result cache করা উচিত।

৩. Consumer — zoo.visitor

// Tourist.java
package zoo.visitor;

import java.util.*;
import zoo.tours.api.*;
import zoo.tours.reservations.*;

public class Tourist {
   public static void main(String[] args) {
      Tour tour = TourFinder.findSingleTour();
      System.out.println("Single tour: " + tour);

      List<Tour> tours = TourFinder.findAllTours();
      System.out.println("# tours: " + tours.size());
   }
}

// module-info.java
module zoo.visitor {
   requires zoo.tours.api;
   requires zoo.tours.reservations;
}

কোনো implementation থাকার আগে রান করলে:

java -p mods -m zoo.visitor/zoo.visitor.Tourist

Single tour: null
# tours: 0
  • findSingleTour() কোনো provider পায় না, তাই enhanced for loop-এর body কখনো চলে না এবং null return হয়।
  • null reference-এর সাথে String concatenation করলে null লেখাটাই print হয় — কোনো NullPointerException হয় না।
  • findAllTours() খালি list return করে (null নয়), তাই size() হয় 0।

৪. Service provider — zoo.tours.agency

// TourImpl.java
package zoo.tours.agency;
import zoo.tours.api.*;

public class TourImpl implements Tour {
   public String name()      { return "Behind the Scenes"; }
   public int length()       { return 120; }
   public Souvenir getSouvenir() {
      return new Souvenir("stuffed animal");
   }
}

// module-info.java
module zoo.tours.agency {
   requires zoo.tours.api;
   provides zoo.tours.api.Tour with zoo.tours.agency.TourImpl;
}

Implementation-যুক্ত package export করা হয়নি — caller যেন সরাসরি তাকে reference না করে। Syntax:

provides interfaceName with className;

Provider package করে একই command আবার চালালে:

Single tour: zoo.tours.agency.TourImpl@1936f0f5
# tours: 1
✓ KEY RULE

কিছুই recompile করা হয়নি। নতুন service provider module যোগ করলে বিদ্যমান module-এর শূন্যটি recompile করতে হয় — service locator নিজেই module path-এ নতুন provider দেখে নেয়। এটাই loose coupling-এর সুবিধা।

⚠ EXAM TRAP

provides-এ আগে interface, পরে implementation, মাঝে with। Exam যেসব ভুল রূপ দেখায়: provides Impl with Interface, provides Interface by Impl, provides Interface using Impl। কেবল with-ই অস্তিত্বশীল।

Section 06

Module আবিষ্কার করা (Discovering)

এই command গুলোর output মুখস্থ করার দরকার নেই। কিন্তু command-এর syntax এবং সেগুলো কী করে — তা জানতেই হবে।

Built-in module চেনা

java.base-এ exam-এর প্রায় সব package আছে। requires java.base কখনোই লিখতে হয় না — এটি সব modular application-এ স্বয়ংক্রিয়ভাবে available। স্পষ্ট করে লিখলেও ফাইল compile হবে, তবে সেটা redundant, তাই বাদ দেওয়াই ভালো। ব্যাপারটা class-এ java.lang স্বয়ংক্রিয়ভাবে import হওয়ার মতোই।

Module nameকী থাকেবইয়ে কভারেজ
java.baseCollections, math, IO, NIO.2, concurrency ইত্যাদিবইয়ের বেশিরভাগ অংশ
java.desktopAWT ও Swingনাম ছাড়া exam-এ নেই
java.loggingLoggingনাম ছাড়া exam-এ নেই
java.sqlJDBCনাম ছাড়া exam-এ নেই
java.xmlXMLনাম ছাড়া exam-এ নেই
⚠ EXAM TRAP
  • java দিয়ে শুরু হওয়া module গুলো আপনার ব্যবহার করার মতো API; jdk দিয়ে শুরু হওয়াগুলো JDK-নির্দিষ্ট। প্রায় ২০টি java.* এবং প্রায় ৩০টি jdk.* module আছে।
  • java.util একটি package, module নয়। jdk.base বলে কিছু নেই — module-টির নাম java.base।
  • তালিকা মুখস্থ করতে হবে না, কিন্তু বানানো নামের ভিড় থেকে আসল module name চিনতে পারতে হবে।

Module describe করা

নিচের দুটি command সমতুল্য:

java -p mods -d zoo.animal.feeding
java -p mods --describe-module zoo.animal.feeding
zoo.animal.feeding file:///absolutePath/mods/zoo.animal.feeding.jar
exports zoo.animal.feeding
requires java.base mandated
  • Declaration-এ কোনো requires না থাকলেও requires java.base mandated দেখা যায় — java.base প্রতিটি module-এ স্বয়ংক্রিয়ভাবে যুক্ত হয়। mandated শব্দটি শেষে বসে।
  • Qualified export দেখায় এভাবে: qualified exports zoo.animal.care.medical to zoo.staff।
  • contains zoo.animal.care.details মানে module-এ এমন একটি package আছে যা একেবারেই export করা হয়নি।
⚠ EXAM TRAP

-d command ভেদে দুই রকম অর্থ বহন করে:

  • javac -d <dir> — class ফাইলের output directory।
  • java -d <module> — --describe-module-এর short form।
  • jar -d — এটিও --describe-module।

Module তালিকা ও resolution দেখা

java --list-modules              // ~70 lines: java.base@21, java.compiler@21, ...
java -p mods --list-modules      // custom module ও তাদের path যোগ হয়

java --show-module-resolution
   -p feeding
   -m zoo.animal.feeding/zoo.animal.feeding.Task

--list-modules

  • Observable module-এর তালিকা দেখায়
  • প্রিন্ট করেই বেরিয়ে যায় — program রান করে না
  • JDK module-এ version (@21), custom module-এ file path

--show-module-resolution

  • Module resolution-এর debugging view
  • প্রচুর output দেয়, তারপর program রান করে (শেষে All fed!)
  • শুরুতে root module দেখায়

jar দিয়ে describe

jar -f mods/zoo.animal.feeding.jar -d
jar --file mods/zoo.animal.feeding.jar --describe-module

Output-এর একমাত্র পার্থক্য — JAR সংস্করণে filename-এ module-info.class যুক্ত থাকে। Exam-এর জন্য যা জরুরি: java ও jar দুটোই module describe করতে পারে।

jdeps — dependency জানা

Describe-এর বিপরীতে jdeps module declaration-এর পাশাপাশি আসল code-ও দেখে, তাই কোন dependency আসলে ব্যবহৃত হচ্ছে তা বলে দেয়, শুধু ঘোষিত নয়। যেসব প্রজেক্ট এখনো modularize হয়নি, তাদের জন্য এটাই টুল।

  • jdk.unsupported প্রকাশিত module তালিকায় নেই — এতে internal library আছে যা ব্যবহার করা উচিত নয়, ভবিষ্যতে হারিয়ে যেতে পারে।
  • jdeps-এর --module-path option-এর কোনো short form নেই, অন্য command-এর মতো নয়।

jmod

Oracle বেশিরভাগ module-এর জন্য JAR ফাইল সুপারিশ করে। JMOD ফাইল শুধু তখনই সুপারিশ করা হয় যখন native library বা এমন কিছু থাকে যা JAR-এ রাখা যায় না। মনে রাখার মূল কথা: jmod শুধু JMOD ফাইল নিয়ে কাজ করে।

jlink ও jpackage

jlink --module-path mods --add-modules zoo.animal.talks --output zooApp

এটি তৈরি করে runtime image: একটি folder যাতে থাকে bin, conf, include, legal, lib, man এবং একটি release ফাইল — zip করলে প্রায় ১৫ MB, যেখানে পুরো JDK ১৫০ MB+। এটি একক "image file" নয়।

jpackage --name feedingTask --module-path mods
   --module zoo.animal.feeding/zoo.animal.feeding.Task

এটি তৈরি করে application image: নির্দিষ্ট platform-এর জন্য একটি একক executable (Windows-এ .exe, Mac-এ .dmg — এখানে feedingTask-1.0.dmg)। Non-modular JAR-এর জন্য:

jpackage --name myApp --input myDir --main-class com.wiley.java.Cat
   --main-jar myApp.jar

jlink

  • Output: runtime image = একটি directory
  • শুধু modular application
  • -p/--module-path, --add-modules, --output

jpackage

  • Output: application image = একক executable
  • Modular ও non-modular — দুটোই
  • -n/--name, -i/--input, --main-class, --main-jar, --app-version (default 1.0)

দুটোই Java-র প্রয়োজনীয় অংশ সরবরাহ করে, এবং দুটোর ক্ষেত্রেই target system-এ আগে থেকে JDK ইনস্টল থাকার দরকার নেই।

Section 07

Module-এর প্রকারভেদ তুলনা

Named module

Named module-এ JAR-এর root-এ package-গুলোর পাশে একটি module-info.java ফাইল থাকে, এবং এটি থাকে module path-এ। আলাদা করে কিছু না বললে যেকোনো module-ই named module। মনে রাখার কৌশল: named module-এর নাম থাকে module-info.java-র ভেতরে, আর নিজে থাকে module path-এ।

★ REMEMBER

অধ্যায় ৭ থেকে: sealed class-এর subclass ভিন্ন package-এ রাখার একমাত্র উপায় হলো একই named module-এর ভেতরে থাকা।

Automatic module

Automatic module module path-এ থাকে কিন্তু এতে module-info.java থাকে না — একটি সাধারণ JAR-কে module path-এ রাখলে সেটি module হিসেবে গণ্য হয়। Java নিজেই module name ঠিক করে নেয়, এবং একে reference করা code এমনভাবে আচরণ করে যেন module-info.java উপস্থিত। এটি স্বয়ংক্রিয়ভাবে সব package export করে।

Library লেখকদের উৎসাহিত করা হয়েছিল META-INF/MANIFEST.MF-এ Automatic-Module-Name property দিয়ে তাদের ইচ্ছাকৃত module name ঘোষণা করতে। Manifest হলো colon দিয়ে আলাদা করা key/value জোড়ার একটি text ফাইল; Java 21-এর default:

Manifest-Version: 1.0
Created-By: 21 (Oracle Corporation)

Automatic module name নির্ধারণের algorithm

  1. MANIFEST.MF-এ Automatic-Module-Name থাকলে সেটাই ব্যবহার হবে, এখানেই শেষ।
  2. JAR নাম থেকে file extension সরান।
  3. নামের শেষ থেকে version information সরান। Version মানে digit ও dot, শেষে বাড়তি তথ্য থাকতে পারে — যেমন -1.0.0 বা -1.0-RC।
  4. অবশিষ্ট যেসব character letter বা number নয়, সেগুলো dot দিয়ে প্রতিস্থাপন করুন।
  5. পরপর একাধিক dot-কে একটি dot বানান।
  6. ফলাফলের প্রথম বা শেষ character dot হলে সেটি সরিয়ে ফেলুন।

  • emily-1.0.0.jar → emily · emily-1.0.0-SNAPSHOT.jar → emily (শেষের tag version-এর সাথেই চলে যায়)।
  • emily_the_cat-1.0.0.jar → emily.the.cat। Underscore হয় dot, dash নয় — আর module name-এ dash কখনোই allowed নয়।
  • emily.$.jar → emily। $ হয় dot, ফলে emily.., তা সংকুচিত হয়ে emily., শেষে trailing dot সরে যায়।

Unnamed module

Unnamed module থাকে classpath-এ। Automatic module-এর মতোই এটি সাধারণ JAR; পার্থক্য হলো এটি module path-এ নয়, classpath-এ। তাই একে পুরোনো code এবং module-এর তুলনায় দ্বিতীয় শ্রেণির নাগরিক হিসেবে ধরা হয়। সাধারণত এতে module-info.java থাকে না; যদি থেকেও যায়, সেটি উপেক্ষা করা হয়, কারণ এটি classpath-এ আছে। Unnamed module named module-কে কোনো package export করে না, তবে classpath বা module path-এর যেকোনো JAR পড়তে পারে।

✓ KEY RULE

Classpath-এর code module path access করতে পারে। কিন্তু module path-এর code classpath থেকে পড়তে পারে না। এই একটিমাত্র অসমতা exam-এর অনেক প্রশ্নের উত্তর দিয়ে দেয়।

Section 08

Application Migration

ক্রম নির্ধারণ (Determining the order)

প্রজেক্টগুলোর মধ্যে dependency একটি graph তৈরি করে। তীর যায় যে প্রজেক্ট dependency চায় তার থেকে যে প্রজেক্ট সেটা সরবরাহ করে তার দিকে — module-এর ভাষায়, requires থেকে exports-এর দিকে। যেসব প্রজেক্টের কোনো dependency নেই তারা নিচে; যারা অন্যের উপর নির্ভরশীল তারা উপরে। দুটি প্রজেক্টের মাঝে তীর না থাকলে যেকোনো ক্রমই চলে।

Bottom-up migration

  1. এখনো migrate হয়নি এমন সবচেয়ে নিচের প্রজেক্ট বেছে নিন।
  2. module-info.java যোগ করুন — উপরের JAR যেসব package ব্যবহার করে তাদের exports, আর নিজের dependency-র জন্য requires।
  3. ওই named module-কে classpath থেকে module path-এ সরান।
  4. যেগুলো এখনো migrate হয়নি সেগুলো classpath-এ unnamed module হিসেবেই থাকুক।
  5. পরের নিচের প্রজেক্ট নিয়ে পুনরাবৃত্তি করুন।

উপযুক্ত যখন আপনি প্রতিটি JAR নিজে convert করতে পারেন। মাঝপথে মিশ্রণ: named + unnamed।

Top-down migration

  1. সব প্রজেক্ট module path-এ রাখুন।
  2. এখনো migrate হয়নি এমন সবচেয়ে উপরের প্রজেক্ট বেছে নিন।
  3. module-info.java যোগ করে ওই automatic module-কে named module বানান; requires-এ অন্যদের automatic module name ব্যবহার করুন।
  4. পরের উপরের প্রজেক্ট নিয়ে পুনরাবৃত্তি করুন।

উপযুক্ত যখন প্রতিটি JAR আপনার নিয়ন্ত্রণে নেই। মাঝপথে মিশ্রণ: named + automatic।

যে প্রজেক্টের কোনো dependency নেইModule path-এ named moduleModule path-এ automatic module
⚠ EXAM TRAP

"Top-down migration-এ named module ছাড়া বাকি সব module হলো ______ এবং থাকে ______-এ।" → automatic, module path। Top-down শুরুই হয় সবকিছু module path-এ রেখে, তাই classpath-এ কিছুই থাকে না।

বড় প্রজেক্ট module-এ ভাগ করা

Package গুলোকে যৌক্তিক গ্রুপে ভাগ করে dependency আঁকুন। Package-এর চেয়ে module সাধারণত কম হয়, কারণ কিছু package একই module ভাগ করে নেয়। JPMS cyclic dependency অনুমোদন করে না: zoo.tickets.delivery যদি zoo.tickets.discount-কে requires করে, তবে zoo.tickets.discount আর zoo.tickets.delivery-কে requires করতে পারবে না। প্রচলিত সমাধান হলো — শেয়ার করা code নিয়ে নতুন একটি module তৈরি করা, যাতে চক্রটি ভেঙে যায়।

Cyclic dependency-তে compile ব্যর্থ হওয়া

// Butterfly.java
package zoo.butterfly;
public class Butterfly {
   private Caterpillar caterpillar;
}
// module-info.java
module zoo.butterfly {
   exports zoo.butterfly;
   requires zoo.caterpillar;
}

// Caterpillar.java
package zoo.caterpillar;
public class Caterpillar {
   Butterfly emergeCocoon() { // logic omitted }
}
// module-info.java
module zoo.caterpillar {
   exports zoo.caterpillar;
   requires zoo.butterfly;   // stalemate — neither module can be compiled
}
  • zoo.caterpillar তৈরি না হওয়া পর্যন্ত zoo.butterfly compile হবে না।
  • zoo.butterfly তৈরি না হওয়া পর্যন্ত zoo.caterpillar compile হবে না।
  • ফলে কোনোটিই কখনো compile হবে না। Module system compile-time-এই cyclic dependency আটকে দেয় — এটি bug নয়, feature।
  • তিনটি module-এও একই নিয়ম: ballA requires ballB, ballB requires ballC হলে ballC আর ballA-কে requires করতে পারবে না।
✓ KEY RULE

একই module-এর package গুলোর মধ্যে cyclic dependency Java অনুমোদন করে। নিষেধ শুধু module-এর মধ্যে চক্রে। একটি cyclic dependency-তে অন্তত দুটি requires statement লাগে, এবং দুই বা তার বেশি module জড়িত থাকতে পারে।

সংক্ষিপ্ত রিভিউ

Modules-এর পরিচয়

  • JPMS = module JAR-এর format + JDK-র partitioning + বাড়তি command-line option; এটি JAR hell সমাধান করে।
  • Module = এক বা একাধিক package + module-এর root-এ module-info.java।

তৈরি ও চালানো

  • javac -p mods -d outDir files… module-info.java; java -p mods -m moduleName/package.ClassName; jar -cvf mods/x.jar -C dir/ .
  • Module ও class-এর মাঝে একটি slash; বাকি সব জায়গায় dot। Module name-এ dot চলে, dash কখনোই নয়।

Directives

  • exports (চাইলে to), requires / requires transitive, opens (চাইলে to), provides … with …, uses। যেকোনো ক্রমে।
  • একই module দুটি requires clause-এ থাকলে compile হয় না; open module + opens একসাথেও compile হয় না।
  • Package export না করলে public-ও module-এর বাইরে পৌঁছায় না।

Services

  • Service = service provider interface + service locator। Service provider (implementation) ও consumer service-এর অংশ নয়।
  • SPI: exports। Locator: exports, requires, uses। Provider: requires, provides। Consumer: requires।
  • ServiceLoader.load() iterable; stream() দেয় Stream<Provider<S>>, তাই .map(Provider::get) লাগে।

Module আবিষ্কার

  • java -d / --describe-module, --list-modules (রান করে না), --show-module-resolution (রান করে), jar -f x.jar -d।
  • jdeps (-s/-summary, --jdk-internals/-jdkinternals); JMOD ফাইলের জন্য jmod; jlink → directory; jpackage → executable।
  • প্রতিটি module-এর describe output-এ requires java.base mandated দেখা যায়।

Module-এর প্রকার

  • Named = module-info + module path। Automatic = module-info নেই + module path, সব export করে। Unnamed = classpath, named module-কে কিছুই export করে না।
  • Automatic module name: manifest আগে; না থাকলে extension ও version বাদ, special character → dot, dot সংকোচন, প্রান্তের dot ছাঁটাই।

Migration

  • Bottom-up: নিচ থেকে শুরু, বাকিরা classpath-এ unnamed। Top-down: আগে সব module path-এ, বাকিরা automatic।
  • Module-এর মধ্যে চক্র কখনো compile হয় না; একই module-এর package-এর মধ্যে চক্র ঠিক আছে।

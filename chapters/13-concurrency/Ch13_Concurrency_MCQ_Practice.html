Q2ReentrantLock

Given that the sum of the numbers from 1 (inclusive) to 10 (exclusive) is 45, what are the possible results of executing this program?

4:  private Lock vault = new ReentrantLock();
5:  private int total = 0;
6:  public void deposit(int value) {
7:     try {
8:        vault.tryLock();
9:        total += value;
10:    } finally { vault.unlock(); }
11: }
14: IntStream.range(1, 10).parallel().forEach(s -> bank.deposit(s));
16: System.out.println(bank.total);

Choose all that apply.

  • A. 45 is printed.
  • B. A number less than 45 is printed.
  • C. A number greater than 45 is printed.
  • D. An exception is thrown.
Show Answer
A · D

tryLock() returns immediately with false if the lock cannot be acquired, and this code never checks the return value on line 8 — so the protected code runs either way. When tryLock() happens to return true on every call, the program completes and prints 45 (A). On any execution where it returns false at least once, line 10 throws IllegalMonitorStateException (D). B would only be possible if line 10 did not throw.

Q5Atomic

What statement about the following code is true?

var value1 = new AtomicLong(0);
final long[] value2 = {0};
IntStream.iterate(1, i -> 1).limit(100).parallel()
   .forEach(i -> value1.incrementAndGet());
IntStream.iterate(1, i -> 1).limit(100).parallel()
   .forEach(i -> ++value2[0]);
System.out.println(value1 + " " + value2[0]);
  • A. It outputs 100 100.
  • B. It outputs 100 99.
  • C. The output cannot be determined ahead of time.
  • D. The code does not compile.
Show Answer
C

The code compiles and runs without exception. The first value is always 100 because AtomicLong.incrementAndGet() is atomic. The second is nondeterministic — ++ is not atomic, so threads can overwrite each other's work and any value from 1 to 100 is possible. Since one part varies, the overall output cannot be predicted.

Q6Parallel streams

Q7Threading problems

Fill in the blanks: __________ occur(s) when two or more threads are blocked forever but both appear active. __________ occur(s) when two or more threads try to complete a related task at the same time, resulting in invalid or unexpected data.

  • A. Livelock, Deadlock
  • B. Deadlock, Starvation
  • C. Livelock, Race conditions
  • D. Starvation, Race conditions
Show Answer
C

Livelock is when threads are conceptually blocked forever although each is still active and trying to complete its task — "appear active" is the discriminator against deadlock. A race condition is the undesirable result when two tasks that should be sequential complete at the same time. Starvation is a single thread perpetually denied a resource, which doesn't match either blank.

Q8run vs start

Assuming this class is accessed by only a single thread at a time, what is the result of calling countIceCreamFlavors()?

private static int counter;
public static void countIceCreamFlavors() {
   counter = 0;
   Runnable task = () -> counter++;
   LongStream.range(0, 500)
      .forEach(m -> Thread.ofPlatform()
        .priority(1)
        .unstarted(task)
        .run());
   System.out.println(counter);
}
  • A. The method consistently prints a number less than 500.
  • B. The method consistently prints 500.
  • C. The method prints a value that cannot be determined ahead of time.
  • D. The method does not compile.
Show Answer
B

Be wary of run() vs start(). Although this looks concurrent, run() executes synchronously — each iteration of forEach() waits for it to finish before moving on, so the code is thread-safe and consistently prints 500. If start() had been used (or the stream were parallel), the output would be indeterminate and C would be correct.

Q9ExecutorService

Which are true of ExecutorService?

Choose all that apply.

  • A. If a task is submitted when no threads are available, the executor discards the task without completing it.
  • B. If a task is submitted when no threads are available, the executor adds the task to an internal queue and completes it when a thread is free.
  • C. Platform threads can be pooled using ExecutorService, but not virtual threads.

When no thread is available, the submit call returns immediately and the task is queued internally (B). Only platform threads are pooled (C) — virtual threads are so lightweight that they don't benefit from pooling, which is why the factory method is named newVirtualThreadPerTaskExecutor().

Q10Concurrent collections

What is the result of executing the following code snippet?

SequencedCollection<Integer> lions = new ArrayList<>(List.of(1, 2, 3));
SequencedCollection<Integer> tigers = new CopyOnWriteArrayList<>(lions);
Set<Integer> bears = new ConcurrentSkipListSet<>();
bears.addAll(lions);
for (Integer item: tigers) tigers.add(4);   // x1
for (Integer item: bears) bears.add(5);     // x2
System.out.println(lions.size() + " " + tigers.size() + " " + bears.size());
  • A. It outputs 3 6 4.
  • B. It outputs 6 6 6.
  • C. It compiles but throws an exception at runtime on line x1.
  • D. It compiles but enters an infinite loop at runtime.
Show Answer
A

CopyOnWriteArrayList preserves the original list on iteration, so the first loop runs exactly three times and grows tigers to six. Q11Parallel streams

What statement about the following code is true?

Integer i1 = List.of(1, 2, 3, 4, 5).stream().findAny().get();

Q12Shutdown

Assuming each call to takeNap() takes five seconds without throwing an exception, what is the expected result?

public void shutdown() throws InterruptedException {
   var service = Executors.newFixedThreadPool(4);
   try {
      service.execute(() -> takeNap());
      service.execute(() -> takeNap());
      service.execute(() -> takeNap());
   } finally { service.shutdown(); }
   service.awaitTermination(2, TimeUnit.SECONDS);
   System.out.println("DONE!");
}
public void refactored() {
   try (var service = Executors.newFixedThreadPool(4)) {
      service.execute(() -> takeNap());
      service.execute(() -> takeNap());
      service.execute(() -> takeNap());
   }
   System.out.println("DONE!");
}

Choose all that apply.

  • A. shutdown() pauses for approximately 2 seconds and then prints DONE!.
  • B. shutdown() pauses for approximately 15 seconds and then prints DONE!.
  • C. refactored() pauses for approximately 2 seconds and then prints DONE!.
  • D. refactored() pauses for approximately 5 seconds and then prints DONE!.
Show Answer
A · D

awaitTermination() waits the specified amount of time for the tasks to complete; since each five-second task is still running, it returns false after two seconds without throwing, so A is correct. The refactored version uses try-with-resources, which lets the tasks finish gracefully — with a pool of four and three tasks running concurrently, that's about five seconds (D).

Q14Deadlock

What statements about the following code snippet are true?

Object o1 = new Object();
Object o2 = new Object();
try (var service = Executors.newFixedThreadPool(2)) {
   var f1 = service.submit(() -> {
      synchronized (o1) {
         synchronized (o2) { System.out.print("Tortoise"); }
      } });
   var f2 = service.submit(() -> {
      synchronized (o2) {
         synchronized (o1) { System.out.print("Hare"); }
      } });
   f1.get();
   f2.get();
}

Choose all that apply.

  • A. The code will always output Tortoise followed by Hare.
  • B. If the code does output anything, the order cannot be determined.
  • C. The code compiles but may produce a deadlock at runtime.
  • D. The code compiles but may produce a livelock at runtime.
Show Answer
B · C

Both tasks go to the same pool, so the order cannot be determined (B). The resources o1 and o2 are locked in opposite orders, so if the first thread grabs o1 and the second grabs o2 before either gets its second lock, the code hangs — a deadlock (C). It cannot be a livelock, since both threads are simply waiting rather than actively retrying. Note that a deadlock throws no exception.

Q17ReentrantLock

Which statement about methods in ReentrantLock is correct?

  • A. The lock() method will attempt to acquire a lock without waiting indefinitely for it.

Q31Scheduling

A task is submitted with service.scheduleWithFixedDelay(task, 0, 2, TimeUnit.MINUTES). The task starts running at 12:00 and takes five minutes to finish. When does the next execution start?

  • A. 12:02
  • B. 12:05
  • C. 12:07
  • D. 12:10
Show Answer
C

scheduleWithFixedDelay() measures the delay between the termination of one execution and the commencement of the next, so the task ends at 12:05 and the next begins two minutes later at 12:07. Had this been scheduleAtFixedRate(), a new task would have been submitted at 12:02 regardless of whether the previous one had finished.

Quick Revision — the chapter's core traps

  • run() vs start(): run() executes synchronously on the current thread, which quietly makes unsafe code deterministic. Only start() spawns a thread.
  • Virtual threads: always daemons, always priority 5 (setPriority() is a no-op), never pooled. Only newVirtualThreadPerTaskExecutor() creates them.
  • execute() vs submit(): execute() returns void — assigning it to a Future doesn't compile. get() on a Runnable's Future always returns null.
  • Callable lambdas: no parameters, must return a value. Callable can throw checked exceptions; Runnable cannot.
  • Executors: an executor left un-closed keeps the JVM alive forever. awaitTermination() returns false on timeout rather than throwing.
  • Scheduling: the reference type must be ScheduledExecutorService; scheduleAtFixedRate and scheduleWithFixedDelay accept only Runnable. Fixed delay is measured after the task ends.
  • Atomicity: ++ is read-then-write, so neither plain nor volatile fields are safe. Atomic classes preserve every value but not ordering; synchronized preserves both.
  • Monitors: a static synchronized method locks the class object, not the instance — they don't exclude each other. Synchronizing task submission doesn't synchronize task execution.
  • ReentrantLock: lock() blocks forever, tryLock() doesn't; always check tryLock()'s result. Unlock once per acquisition, or you'll hit IllegalMonitorStateException or a stuck lock. Fairness defaults to false.
  • CyclicBarrier: if fewer threads than the limit call await(), it hangs silently. It is reusable once broken.
  • Collections: ConcurrentModificationException can happen with one thread. CopyOnWriteArrayList iterates the original snapshot while still growing. Skip = sorted concurrent.
  • Liveness: deadlock hangs without an exception; livelock threads look active; starvation is one thread denied. Race conditions produce invalid data.
  • Parallel streams: parallelStream() is on Collection, parallel() is on Stream, and there is no ParallelStream class. findAny() is never guaranteed; findFirst() is.
  • Reductions: use a true identity and an order-independent accumulator. Check accumulator parameter types. toSet() is not a parallel reduction; toConcurrentMap() and groupingByConcurrent() are.

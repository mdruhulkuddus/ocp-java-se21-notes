SECTION 01

Understanding Exceptions

An exception is Java's way of saying "I give up — you deal with it." A method can either handle the exception itself, or declare it and make it the caller's problem. All exception events are represented by objects of the Throwable class hierarchy — and not all of them have "Exception" in their name.

The Throwable hierarchy

                java.lang.Throwable
                /                 \
      java.lang.Exception     java.lang.Error   // Error = unchecked, don't touch
             |
   java.lang.RuntimeException                   // RuntimeException = unchecked

// Exception (but NOT RuntimeException) = CHECKED
TypeHow to recognizeOK for program to catch?Required to handle or declare?
Unchecked exceptionSubclass of RuntimeExceptionYesNo
Checked exceptionSubclass of Exception but not of RuntimeExceptionYesYes
ErrorSubclass of ErrorNoNo
✓ KEY RULE — Handle or Declare

Every checked exception that could be thrown inside a method must either be wrapped in a compatible try/catch or declared with throws in the method signature. Unchecked exceptions (RuntimeException, Error) never require this — but declaring them redundantly still compiles.

void fall(int distance) throws IOException {   // declare…
   if(distance > 10) { throw new IOException(); }
}

void fall(int distance) {                       // …or handle
   try {
      if(distance > 10) { throw new IOException(); }
   } catch (Exception e) {          // superclass catch is fine
      e.printStackTrace();
   }
}
★ REMEMBER

Throwable is the parent of everything, including Error. You can catch Throwable/Error, but you should not. Error means something so bad (out of memory, disk gone) that recovery isn't realistic.

SECTION 02

Throwing an Exception

throw

  • A statement inside a code block.
  • Actually throws (or rethrows) an exception object.
  • throw new RuntimeException();

throws

  • Appears only at the end of a method declaration.
  • Declares that the method might throw — it also might not.
  • void fall() throws IOException {}

An exception is an object — you can store it in a reference and throw it later:

var e = new RuntimeException();
throw e;                          // legal

throw RuntimeException();         // DOES NOT COMPILE — missing new!
⚠ EXAM TRAP — Unreachable code after throw 
try {
   throw new RuntimeException();
   throw new ArrayIndexOutOfBoundsException();  // DOES NOT COMPILE
} catch (Exception e) {}

The first throw makes the second statement unreachable → compiler error.

Calling methods that throw checked exceptions

class NoMoreCarrotsException extends Exception {}

public class Bunny {
   private void eatCarrot() throws NoMoreCarrotsException {}
   public void hopAround() {
      eatCarrot();                // DOES NOT COMPILE
   }
}

The caller must also handle or declare — even if eatCarrot() never actually throws. Merely declaring the checked exception is enough to force the caller.

⚠ EXAM TRAP — Catching a checked exception that can't be thrown 
private void eatCarrot() {}          // declares nothing
public void bad() {
   try { eatCarrot(); }
   catch (NoMoreCarrotsException e) { // DOES NOT COMPILE
      System.out.print("sad rabbit");
   }
}

If nothing in the try block can throw the checked exception, the catch is unreachable → compiler error. This rule does not apply to unchecked exceptions (catching RuntimeException is always allowed) or to Exception declared broadly.

Overriding methods with exceptions

OVERRIDING + CHECKED EXCEPTIONS

  1. An overridden method may NOT declare new or broader checked exceptions than the inherited method.
  2. Declaring fewer exceptions, none, or a subclass of the declared exception is perfectly legal.
  3. Unchecked exceptions can be declared freely — they're never part of the contract.
class Hopper { public void hop() {} }
public class Bunny extends Hopper {
   public void hop() throws CanNotHopException {}  // DOES NOT COMPILE
}
// Reverse direction is fine: parent throws, child declares nothing.

Printing an exception — three ways

} catch (Exception e) {
   System.out.println(e);              // java.lang.RuntimeException: cannot hop
   System.out.println(e.getMessage()); // cannot hop
   e.printStackTrace();                // full stack trace with method hierarchy
}
SECTION 03

Recognizing Exception Classes

You must recognize three groups — unchecked (RuntimeException), checked, and Error — plus who throws them (JVM vs. programmer) and the two inheritance pairs.

Unchecked (RuntimeException) classes

ExceptionThrown when…Thrown by
ArithmeticExceptionDividing an int by zero: 11 / 0JVM
ArrayIndexOutOfBoundsExceptionIllegal array index (e.g. -1, or index == length)JVM
ClassCastExceptionCast to a class the object isn't an instance ofJVM
NullPointerExceptionMember access on a null referenceJVM
IllegalArgumentExceptionMethod receives an illegal/inappropriate argumentProgrammer
NumberFormatExceptionConverting a non-numeric String: Integer.parseInt("abc")Programmer (via API)
✓ KEY RULE — Two inheritance pairs the exam loves
  • NumberFormatException extends IllegalArgumentException
  • FileNotFoundException and NotSerializableException extend IOException

These decide catch-block ordering and multi-catch legality (Sections 04–05).

ClassCastException — compile time vs runtime

String type = "moose";
Integer number = (Integer) type;   // DOES NOT COMPILE (unrelated types)

String type = "moose";
Object obj = type;
Integer number = (Integer) obj;    // compiles, but ClassCastException at runtime

Helpful NullPointerException

public class Frog {
   static String name;
   public void hop() {
      System.out.print(name.toLowerCase() + " is hopping");
   }
   public static void main(String[] args) { new Frog().hop(); }
}
// Cannot invoke "String.toLowerCase()" because "Frog.name" is null
  • For instance/static variables, the JVM prints the variable name (Frog.name).
  • For local variables & parameters, it prints <parameterX> / <localX> — the name is lost at compile time — unless compiled with javac -g:vars, which restores real names.

Checked exceptions & Errors

Checked (must handle/declare)

  • IOException — problem reading/writing a file
  • FileNotFoundException — file doesn't exist (subclass of IOException)
  • NotSerializableException — (de)serializing a non-serializable class (subclass of IOException)
  • ParseException — problem parsing input (e.g. NumberFormat.parse())

Errors (unchecked, don't catch)

  • ExceptionInInitializerError — static initializer throws and doesn't handle
  • StackOverflowError — infinite recursion
  • NoClassDefFoundError — class present at compile time, missing at runtime
⚠ EXAM TRAP

When answer choices include both "does not compile" and "throws an exception": code calling a method on a null reference or using an invalid array/List index compiles fine — the answer is runtime exception, not compiler error.

SECTION 04

try / catch & Chaining catch Blocks

TRY STATEMENT SYNTAX RULES

  1. Braces {} are required for try and catch blocks (unlike if/loops).
  2. A traditional try must be followed by catch and/or finally — a "lonely try" does not compile.
  3. The words block and clause are used interchangeably on the exam.
try                     // DOES NOT COMPILE — missing braces
   fall();
catch (Exception e)
   System.out.println("get up");

try {                   // DOES NOT COMPILE — lonely try, no catch/finally
   fall();
}

Chaining catch blocks — order matters

At most one catch block runs: the first one that can handle the exception. If a superclass catch appears before a subclass catch, the subclass catch is unreachable → compiler error.

try {
   seeAnimal();
} catch (ExhibitClosed e) {              // superclass first…
   System.out.print("not today");
} catch (ExhibitClosedForLunch e) {      // DOES NOT COMPILE — unreachable
   System.out.print("try back later");
}
⚠ EXAM TRAP — Hidden subclass ordering 
try {
} catch (IllegalArgumentException e) {
} catch (NumberFormatException e) {   // DOES NOT COMPILE
}

NumberFormatException IS-A IllegalArgumentException, so the second block is unreachable. Same trick works with FileNotFoundException after IOException.

⚠ EXAM TRAP — catch variable scope 
} catch (NumberFormatException e1) {
   System.out.println(e1);
} catch (IllegalArgumentException e2) {
   System.out.println(e1);            // DOES NOT COMPILE — e1 out of scope
}

The exception variable is in scope only inside its own catch block.

SECTION 05

Multi-catch Blocks

A multi-catch block catches multiple exception types with one handler, separated by pipes (|) — with one variable name, written once, at the end.

try {
   System.out.println(Integer.parseInt(args[1]));
} catch (ArrayIndexOutOfBoundsException | NumberFormatException e) {
   System.out.println("Missing or invalid input");
}
catch(Exception1 e | Exception2 e | Exception3 e)    // DOES NOT COMPILE
catch(Exception1 e1 | Exception2 e2 | Exception3 e3) // DOES NOT COMPILE
catch(Exception1 | Exception2 | Exception3 e)        // compiles ✓
⚠ EXAM TRAP — Related types are redundant 
try {
   throw new IOException();
} catch (FileNotFoundException | IOException p) {}  // DOES NOT COMPILE

A subclass and its superclass may not share one multi-catch — the subclass is redundant ("already caught by the alternative IOException"). Fix: just catch IOException.

Chained catch blocks

  • Order matters: subclass before superclass.
  • Each block has its own variable.

Multi-catch (single block)

  • Order of types does not matter.
  • One shared variable at the end; no subclass/superclass pairs allowed.
SECTION 06

The finally Block

FINALLY RULES

  1. Order is fixed: try → catch → finally. Wrong order does not compile.
  2. catch is optional when finally is present (try+finally is legal).
  3. If a try-with-finally is entered, finally always executes — whether or not an exception is thrown.
  4. Exception #1: System.exit() in try/catch — finally does not run.
  5. finally always starts, but may not finish (it can itself throw, e.g. NPE).
try {                // DOES NOT COMPILE — catch after finally
   fall();
} finally {
   System.out.println("all better");
} catch (Exception e) {
   System.out.println("get up");
}

Classic output-tracing question

StringBuilder sb = new StringBuilder();
try {                 sb.append("t");
} catch (Exception e) { sb.append("c");
} finally {           sb.append("f");
}
sb.append("a");
System.out.print(sb.toString());   // tfa
  • No exception → try appends t, catch skipped.
  • finally always runs → f.
  • Execution continues after the try statement → a. Output: tfa.
⚠ EXAM TRAP — return inside finally wins 
int goHome() {
   try {
      // Optionally throw an exception here
      System.out.print("1");  return -1;
   } catch (Exception e) {
      System.out.print("2");  return -2;
   } finally {
      System.out.print("3");  return -3;
   } }

Prints 13 (no exception) or 23 (exception) — but the return value is always -3. The finally block runs just before the method completes and interrupts any earlier return.

SECTION 07

Try-with-Resources

Try-with-resources (a.k.a. automatic resource management) automatically closes all resources opened in the try clause. The compiler rewrites it into a try + implicit finally that calls close().

TRY-WITH-RESOURCES RULES

  1. Only types implementing AutoCloseable may be used (Closeable extends AutoCloseable, both work).
  2. Resources are separated by semicolons (;); each declaration needs its own data type (var is fine).
  3. catch and finally are both optional (unlike a traditional try).
  4. Resources are closed at the end of the try block, in the REVERSE of declaration order.
  5. The implicit finally (close calls) runs before any programmer-defined catch/finally.
  6. Resource variables are in scope only inside the try block.
interface AutoCloseable {
   public void close() throws Exception;   // impl may throw subclass or nothing
}

try (String reptile = "lizard") {}          // DOES NOT COMPILE — String isn't AutoCloseable

try (MyFileClass is = new MyFileClass(1),   // DOES NOT COMPILE — comma + missing type
   os = new MyFileClass(2)) {}
try (MyFileClass ab = new MyFileClass(1),   // DOES NOT COMPILE — comma instead of ;
   MyFileClass cd = new MyFileClass(2)) {}

Order of operations — memorize this output

public class MyFileClass implements AutoCloseable {
   private final int num;
   public MyFileClass(int num) { this.num = num; }
   @Override public void close() { System.out.println("Closing: " + num); }
}

try (MyFileClass bookReader = new MyFileClass(1);
      MyFileClass movieReader = new MyFileClass(2)) {
   System.out.println("Try Block");
   throw new RuntimeException();
} catch (Exception e) {
   System.out.println("Catch Block");
} finally {
   System.out.println("Finally Block");
}
  • Try Block — try body runs, then throws.
  • Closing: 2 then Closing: 1 — implicit finally closes in reverse order, before catch.
  • Catch Block — then Finally Block.

Effectively final resources

A pre-declared variable can be used as a resource (just the name, separated by ;) if it is final or effectively final:

final var bookReader = new MyFileClass(4);
MyFileClass movieReader = new MyFileClass(5);       // effectively final
try (bookReader; var tvReader = new MyFileClass(6); movieReader) {
   System.out.println("Try Block");
} finally { System.out.println("Finally Block"); }
// Try Block → Closing: 5 → Closing: 6 → Closing: 4 → Finally Block
⚠ EXAM TRAP — Not effectively final / use after close 
var writer = Files.newBufferedWriter(path);
try (writer) {          // DOES NOT COMPILE — writer reassigned below
   writer.append("Welcome to the zoo!");
}
writer = null;

// Separately: writing to a resource AFTER its try block compiles
// but throws IOException ("Stream closed") at runtime.
⚠ EXAM TRAP — Scope ends with try block 
try (Scanner s = new Scanner(System.in)) {
   s.nextLine();
} catch(Exception e) {
   s.nextInt();          // DOES NOT COMPILE
} finally {
   s.nextInt();          // DOES NOT COMPILE
}

The resource is already closed and out of scope when catch/finally run.

SECTION 08

Suppressed Exceptions

When more than one exception is thrown, the first is the primary exception; the rest become suppressed exceptions attached to it (retrieved via getSuppressed()). Typical case: the try block throws, then close() also throws.

1: public class JammedTurkeyCage implements AutoCloseable {
2:    public void close() throws IllegalStateException {
3:       throw new IllegalStateException("Cage door does not close");
4:    }
5:    public static void main(String[] args) {
6:       try (JammedTurkeyCage t = new JammedTurkeyCage()) {
7:          throw new IllegalStateException("Turkeys ran off");
8:       } catch (IllegalStateException e) {
9:          System.out.println("Caught: " + e.getMessage());
10:         for (Throwable t: e.getSuppressed())
11:            System.out.println("Suppressed: " + t.getMessage());
12:      } }
  • Line 7 throws the primary exception ("Turkeys ran off").
  • Java auto-calls close() → its exception becomes suppressed.
  • Output: Caught: Turkeys ran off then Suppressed: Cage door does not close.
✓ KEY RULE — catch matches the PRIMARY exception

If the try block throws RuntimeException and close() throws IllegalStateException, a catch (IllegalStateException e) does not match — the primary RuntimeException propagates to the caller (with the suppressed one attached).

✓ KEY RULE — Multiple resources failing

Resources close in reverse order, so if several close() calls throw, the last-declared resource's exception is thrown first → it becomes the primary, and the rest are suppressed.

⚠ EXAM TRAP — finally can LOSE exceptions (not suppress) 
try (JammedTurkeyCage t = new JammedTurkeyCage()) {
   throw new IllegalStateException("Turkeys ran off");
} finally {
   throw new RuntimeException("and we couldn't find them");
}
// Only "and we couldn't find them" propagates — the try-block
// exception (and its suppressed exception) are LOST.

Suppression applies only to exceptions thrown in the try clause (plus close). An exception thrown in a programmer-defined finally simply replaces everything — bad practice, but legal.

SECTION 09

Formatting Numbers — DecimalFormat

NumberFormat is an abstract class with format(double) / format(long). The concrete DecimalFormat takes a pattern String. Only two symbols matter for the exam:

SymbolMeaningExample
#Omit the position if no digit exists for it$2.2
0Put 0 in the position if no digit exists for it$002.20
double d = 1234.567;
NumberFormat f1 = new DecimalFormat("###,###,###.0");
System.out.println(f1.format(d));  // 1,234.6

NumberFormat f2 = new DecimalFormat("000,000,000.00000");
System.out.println(f2.format(d));  // 000,001,234.56700

NumberFormat f3 = new DecimalFormat("Your Balance $#,###,###.##");
System.out.println(f3.format(d));  // Your Balance $1,234.57
  • # positions to the left disappear; the fraction is rounded to fit (.567 → .6, .57).
  • 0 forces leading/trailing zeros to the full pattern width.
  • Commas between unused # positions are removed automatically.

SECTION 11

Internationalization & Locales

Internationalization (i18n)

  • Designing the program so it can be adapted: externalize strings to properties files, use proper formatters.

Localization (l10n)

  • Actually supporting multiple locales: translating strings, locale-correct dates & numbers.

LOCALE FORMAT RULES

  1. Language code: lowercase, always required — e.g. en.
  2. Country code: UPPERCASE, optional, joined by underscore — e.g. en_US.
  3. Valid forms: en and en_US. Nothing else.
US      // invalid — country without language
enUS    // invalid — missing underscore
US_en   // invalid — reversed
EN      // invalid — language must be lowercase

Three (non-deprecated) ways to get a Locale

// 1. Built-in constants
System.out.println(Locale.GERMAN);   // de       (language only)
System.out.println(Locale.GERMANY);  // de_DE    (language + country)

// 2. Factory method
Locale.of("fr");           // fr
Locale.of("hi", "IN");     // hi_IN

// 3. Builder — properties in any order
Locale l1 = new Locale.Builder().setLanguage("en").setRegion("US").build();
Locale l2 = new Locale.Builder().setRegion("US").setLanguage("en").build();
★ REMEMBER
  • The new Locale("en","US") constructors are deprecated — use constants, Locale.of(), or the Builder.
  • Java happily creates invalid locales like xx_XX — no exception, it just won't match anything.
  • Locale.setDefault(locale) affects only that one program run.

Localizing Numbers & CompactNumberFormat

NumberFormat factory methods (java.text)

PurposeFactory method (default or with Locale)

CurrencygetCurrencyInstance()

Rounds decimals before displaygetIntegerInstance()

int attendeesPerMonth = 3_200_000 / 12;
NumberFormat.getInstance(Locale.US).format(attendeesPerMonth);            // 266,666
NumberFormat.getInstance(Locale.GERMANY).format(attendeesPerMonth);       // 266.666
NumberFormat.getInstance(Locale.CANADA_FRENCH).format(attendeesPerMonth); // 266 666

// Currency: $48.00 in en_US, £48.00 in en_GB
// Percent: 0.802 → "80%" (US), "80 %" (Germany)
✓ KEY RULE — parse() is locale-sensitive and CHECKED 
String s = "40.45";
NumberFormat.getInstance(Locale.US).parse(s);     // 40.45
NumberFormat.getInstance(Locale.FRANCE).parse(s); // 40 — '.' isn't a French decimal; parsing stops

String income = "$92,807.99";
double value = (Double) NumberFormat.getCurrencyInstance().parse(income);
System.out.println(value);   // 92807.99 — parse returns Number, cast then unbox

parse() throws a checked ParseException — it must be handled or declared. It returns Number, castable to the wrapper type.

CompactNumberFormat

COMPACT NUMBER RULES

  1. Determine the highest range: thousand (K), million (M), billion (B), trillion (T).
  2. Return up to the first three digits of that range, rounding the last as needed.
  3. Append an identifier: SHORT → symbol (7M); LONG → space + word (7 million).
  4. No style specified → SHORT is the default.
// format(7_123_456) in en_US:
getCompactNumberInstance()                              // 7M
getCompactNumberInstance(Locale.getDefault(), Style.SHORT) // 7M
getCompactNumberInstance(Locale.getDefault(), Style.LONG)  // 7 million
getCompactNumberInstance(Locale.GERMAN, Style.SHORT)    // 7 Mio.
getCompactNumberInstance(Locale.GERMAN, Style.LONG)     // 7 Millionen
getNumberInstance()                                     // 7,123,456

// format(314_900_000) → 315M / 315 million / … (third digit rounds up!)
⚠ EXAM TRAP — Compact parsing quirks 
var compact = NumberFormat.getCompactNumberInstance(Locale.of("en","US"), Style.SHORT);
compact.format(1_000_000);      // 1M
compact.parse("1M");            // 1000000
compact.parse("1000000");       // 1000000
compact.parse("1,000,000");     // 1 — stops at the comma!
compact.parse("$1000000");      // ParseException — can't handle $

Locale.Category — DISPLAY vs FORMAT

var spain = Locale.of("es", "ES");  var money = 1.23;

Locale.setDefault(Locale.of("en", "US"));
printCurrency(spain, money);              // $1.23, Spanish

Locale.setDefault(Category.DISPLAY, spain);
printCurrency(spain, money);              // $1.23, español

Locale.setDefault(Category.FORMAT, spain);
printCurrency(spain, money);              // 1,23 €, español
  • DISPLAY — how data about the locale is displayed (e.g. getDisplayLanguage()).
  • FORMAT — how dates/numbers/currencies are formatted.
  • Locale.setDefault(locale) sets both categories together.
SECTION 14

Resource Bundles

A resource bundle holds locale-specific key/value pairs, commonly in .properties files (keys and values separated by = or :). Filename = bundle name + _locale + .properties.

# Zoo_en.properties
hello=Hello
open=The zoo is open

# Zoo_fr.properties
hello=Bonjour
open=Le zoo est ouvert
var rb = ResourceBundle.getBundle("Zoo", locale);  // or getBundle("Zoo") = default locale
rb.getString("hello");
rb.keySet();   // all keys

Search order — picking the bundle (requested fr_FR, default en_US)

StepLooks for fileReason
1Zoo_fr_FR.propertiesRequested locale
2Zoo_fr.propertiesRequested language, no country
3Zoo_en_US.propertiesDefault locale
4Zoo_en.propertiesDefault locale's language, no country
5Zoo.propertiesDefault bundle (no locale)
6MissingResourceExceptionNothing found
★ REMEMBER — Count-the-files question 
Locale.setDefault(Locale.of("hi"));
ResourceBundle rb = ResourceBundle.getBundle("Zoo", Locale.of("en"));
// Max files considered = 3: Zoo_en, Zoo_hi, Zoo (no countries anywhere)
✓ KEY RULE — Selecting VALUES uses only the matched hierarchy

Once a bundle is matched, keys may come only from it and its parents (drop name components until the top): Zoo_fr_FR → Zoo_fr → Zoo. The default locale's bundle is no longer considered for individual keys.

The classic four-file trace

# Zoo.properties        → name=Vancouver Zoo
# Zoo_en.properties     → hello=Hello, open=is open
# Zoo_en_US.properties  → name=The Zoo
# Zoo_en_CA.properties  → visitors=Canada visitors

Locale.setDefault(Locale.of("en", "US"));
var rb = ResourceBundle.getBundle("Zoo", Locale.of("en", "CA"));
rb.getString("hello");    // Zoo_en   → Hello
rb.getString("name");     // Zoo      → Vancouver Zoo (NOT "The Zoo"!)
rb.getString("open");     // Zoo_en   → is open
rb.getString("visitors"); // Zoo_en_CA → Canada visitors
// Output: Hello. Vancouver Zoo is open Canada visitors

rb.getString("close");    // MissingResourceException — key not in hierarchy
  • Match found immediately: Zoo_en_CA → default locale en_US becomes irrelevant.
  • Hierarchy searched per key: Zoo_en_CA → Zoo_en → Zoo. Zoo_en_US is never used.
SECTION 15

MessageFormat & the Properties Class

MessageFormat — parameter substitution

# property: helloGreeting=Hello, {0} and {1}
String greeting = rb.getString("helloGreeting");
MessageFormat.format(greeting, "Tammy", "Henry");  // Hello, Tammy and Henry

The second parameter of format() is a vararg; {0}, {1}… mark substitution order.

Properties — a String→String map with defaults

var props = new Properties();
props.setProperty("name", "Our zoo");
props.setProperty("open", "10am");

props.getProperty("camel");           // null
props.getProperty("camel", "Bob");    // Bob — default for missing key

props.get("open");                    // 10am
props.get("open", "soon");            // DOES NOT COMPILE — get() takes ONE arg
✓ KEY RULE

Only getProperty() supports a default value. get() (inherited map behavior) takes a single parameter — a two-argument get() is a compiler error.

Short Recap

Exception types

  • Checked = Exception minus RuntimeException → handle or declare. Unchecked = RuntimeException + Error. Never catch Error/Throwable.

throw / throws & overriding

  • throw = statement, throws = declaration; throw RuntimeException() without new doesn't compile. Overrides may declare fewer/narrower checked exceptions, never new/broader ones.

Exception classes

  • NFE extends IAE; FNFE & NotSerializableException extend IOException. JVM throws ArithmeticException/AIOOBE/CCE/NPE; programmers throw IAE/NFE.

try/catch/finally

  • Subclass catch must come before superclass; catch variable scoped to its block; finally always runs (except System.exit()) and a return there overrides earlier returns.

Multi-catch

  • One variable at the end; no subclass–superclass pairs; type order irrelevant.

Try-with-resources

  • AutoCloseable only; semicolon-separated; closes in reverse order via implicit finally that runs before catch/finally; resources scoped to try; pre-declared resources must be (effectively) final.

Suppressed exceptions

  • First thrown = primary, close() failures get suppressed onto it; an exception in a programmer-defined finally replaces (loses) everything.

Formatting

  • DecimalFormat: # omits, 0 pads, fraction rounds. Date symbols: M/m, H/h case-sensitive; wrong symbol for type → runtime exception; escape literals with '…', '' = literal quote.

Locales & localization

  • Format: en or en_US (lowercase lang required, UPPERCASE country optional). Constructors deprecated → constants / Locale.of() / Builder. parse() throws checked ParseException and is locale-sensitive. Compact: 3 digits + K/M/B/T, SHORT default.

Resource bundles

  • Pick bundle: requested (full→lang) → default (full→lang) → base bundle → MissingResourceException. Values come only from the matched hierarchy + parents.
